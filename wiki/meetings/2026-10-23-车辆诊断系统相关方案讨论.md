## 核心结论

### 未来 12 个月

据摘要：

- 要有一张月度进度表，覆盖逆向需求梳理和正向 B1、B2。摘要写 11 月向雷总汇报。
- B1 的目标是人主诊，AI 以影子模式做预诊断，再抬覆盖度、准确率，压诊断时长。
- 逆向：下周跨部门对齐各车型诉求，按车型排落地计划。
- 正向分成 AI 应用和 Alert 埋点。Alert 定义到哪，AI 应用就要消费到哪。
- 第一阶段优先在云端判断。车端执行先谨慎，能力成熟后再下放到车端。

### Alert

据摘要：

- 一条成熟 Alert 要有四件事：触发时的原始现场、根因、自恢复方案、不能自恢复时怎么调度维修资源。
- 成熟度分三级：只能读数据、支持订阅更新、带完整处置方案。
- 进度用一个立方体看，三轴是能力成熟度（看到 / 看清 / 可处置）、功能清单覆盖度、车型研发进度（设计 / 开发 / 验证完成）。
- 沉淀走两条路：服务侧从市场工单和社区经验反推需求；研发按功能域正向设计。目标是把 Alert 对市场问题的覆盖抬到 70%–80%。

章节补充、且摘要没有写进同一句的：

- 章节「阐述打动 Alert 的三年目标」把 Alert 说成诊断结论在车端的表现，云端案例、规则、自动化是诊断结论的云端表现。标题里的「打动」按原文保留。
- 章节「Alert 产生路径」写每月 10 万以上的市场问题，目标覆盖到 70%–80%；社区、插件、自动化对应不同成熟度。摘要只写了 70%–80% 的成熟状态，没有写 10 万。
- 章节写当前 Alert 缺根因、缺维修指引、命名不统一，并写售后要参与 Alert 生产。
- 处置顺序在章节「车辆故障 Alert 的处置方式」里是：先自恢复，再远程操作介入，这两类都不行再匹配维修资源。故障属性由研发定义，处置规则可以配置在云端。
- 度量章节把核心维度写成覆盖度、一次诊断准确率、耗时。摘要的立方体三轴不要和这三项度量合成同一组指标。

### 上报授权

摘要和章节不是同一句，待办也还开着，这里并列：

- **摘要**：现有车联网协议、用户体验改进计划已经覆盖故障数据上报，不必再逐单授权，可以推 Alert 合规上传。
- **章节「讨论车端 Alert 上报的用户授权」**：争议点是 Alert 作为车端运行数据上报要有用户授权；现有逐工单、带有效期的授权不够用。文中提到特斯拉是售车时一次性终身授权。后续对接法务，必要时报到雷总。
- **章节「车机数据采集相关协议」**：卖车时有车联协议和用户体验改进协议。车联不签就不能联网，用户体验改进可以拒签。这两类被写成数据采集的保底依据。售后远程诊断要单独授权。

### B1 链路和演示

据摘要：

- 人主诊不变。用户进线后人工开工单，系统按 Alert 出预诊断报告，不提前主动派单。
- 车端上报的 Alert 都留在云端，预先建好预诊断上下文，给后面的 B2 自动开工单用。
- 车端自闭环：用户能感知的简单故障，车端提示用户自己操作，结果回云端留痕。
- 车云协同：用户解决不了的，转到云端服务工作台，技师远程处理。
- Demo 选昆仑，场景是黑屏和充电。

章节「车载诊断相关度量」另写：初步倾向是 B1 不必提前建全量 Session，接到单、匹配上 Alert 再创建。这句说的是 Session，摘要说的是预诊断上下文，本页不把两者收成同一件事。

黑屏章节还写了：session 里生成工单和诊断报告，同步到客服工作台；用户在 APP 授权后，客服可以远程进服务模式重启。车端和手机端可以同时提醒。面客文案要做合规评审，对应待办里找杰婷问流程。

### 远诊工作台

摘要用「远诊工作台」。章节标题写作「原诊工作台」「原诊微信号输入页面」「原诊工作台」，本页不把这两个词收成同一个产品名。

据摘要：

- 2.5 是过渡：把现有分散功能收拢，加全局检索和个人跟进提醒，先上高频功能，保留原来的操作习惯，再逐步加 AI。
- 3.0 是 AI 原生：技能中心接受第三方诊断 Skill，官方评审后进 Agent 能力池；用户可以分组管理专家 Agent，用对话调用。

### 面向 Agent 的诊断服务

据摘要：

- 策略中枢是中间层，串各域知识、历史工单、技师案例，做知识连接、策略蒸馏、评测和分发。
- 产出：以 Alert 为核心的领域知识库、轻量诊断脚本库、标准化诊断策略集、质量评测集。
- 配套要补 Agent 流量治理、高风险操作管控、对话反馈蒸馏，对应以后 Agent 流量超过人工流量的情况。

章节「关于 Agent 流量及诊断能力的两个重要判断」写了两条判断：Agent 流量未来会超过人类用户；Agent 的诊断能力不会跟着自身智能一起涨，不会无师自通，要把诊断能力提供给 Agent。

章节「介绍 Agent 相关配套基建」点名张举提到的 AI 流量治理，并写高风险操作包括 Agent 能否进入服务模式。材料待办是把晋钊、志浩准备的面向 Agent 诊断治理材料发到项目群，署名为说话人1。
